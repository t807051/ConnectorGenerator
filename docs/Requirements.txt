--------------------------------------------------------------------------------
1. CONNECTOR PROJECT DEFINITION
--------------------------------------------------------------------------------

Connector Projects are defined in a JSON file. Each JSON file contains the
definition of ONE connector project. A connector project consists of one or
more connectors. JSON file structure:

{
  "projectname":        "<projectname>",
  "projectdescription": "<projectdescription>",
  "hosts": [
    {
      "env":            "<environment label>",
      "hostname":       "<base URL>",
      "authentication": "<basic|kong>"
    }
  ],
  "connectors": [
    {
      "connectorid":          "<connectorid>",
      "connectordescription": "<connectordescription>",
      "inputClass":           "<inputClass>",
      "entityClass":          "<entityClass>",
      "dataRecordClass":      "<dataRecordClass>",
      "apiPath":              "<apiPath>",
      "httpMethod":           "<httpMethod>",
      "requestExample":       "<requestExampleFilename>",
      "responseExample":      "<responseExampleFilename>"
    }
  ]
}

Field rules:
  - <projectname>         : Either <sourceSystem> or <sourceSystem>.tmf
                            Always lowercase. e.g. "inventory" or "inventory.tmf"
  - <projectdescription>  : Optional free-text description of the connector project.
                            Used in the generated spec document.
                            Read via .get(); defaults to "" if absent.
  - <hosts>               : Optional list of deployment environment entries.
                            Each entry has:
                              "env"            : Environment label (e.g. "NP", "PR")
                              "hostname"       : Base URL (e.g. "http://hostname.com")
                              "authentication" : "basic" or "kong"
                            Read via .get(); defaults to [] if absent.
                            Used in the generated spec document only.
  - <connectorid>         : Unique identifier for each connector within the project.
                            Used to drive all generated file and class names.
  - <connectordescription>: Optional free-text description of the connector.
                            Read via .get(); defaults to "" if absent.
                            Used in the generated spec document only.
  - <inputClass>          : Name of the input/request class for this connector.
  - <entityClass>         : Name of the entity class for this connector.
  - <dataRecordClass>     : Name of the data record class for this connector.
  - <apiPath>             : REST API endpoint path. e.g. "/inventory/v1/items/{id}"
  - <httpMethod>          : HTTP method. e.g. GET, POST, PUT, PATCH, DELETE
  - <requestExampleFilename>  : Filename of the request example JSON file,
                                located in the same directory as the definition
                                file. Used to generate IDL fields for
                                <connectorid>Request and the request POJO class.
                                Optional — omit or set null if not applicable.
  - <responseExampleFilename> : Filename of the response example JSON file,
                                located in the same directory as the definition
                                file. Used to generate IDL fields for
                                <connectorid>Entity and the response POJO class.
                                Optional — omit or set null if not applicable.

Validation rules:
  - JSON file must exist and must not be empty.
  - File must be valid JSON (UTF-8, BOM-safe).
  - "projectname" field is required.
  - "connectors" field is required and must be a non-empty list.
  - Each connector entry must contain all six core fields:
    connectorid, inputClass, entityClass, dataRecordClass, apiPath, httpMethod.
  - projectdescription, hosts, connectordescription, requestExample, and
    responseExample are optional fields (read via .get()).

3. SCRIPT REQUIREMENTS
--------------------------------------------------------------------------------

- Script written in Python (standard library only — no third-party packages).
- Script reads connector definition from a JSON file passed as a command-line
  argument. Usage: python main.py <definition.json>
- Script creates a connector project by:
    a) Copying template directories to target locations.
    b) Editing copied files with data from the connector definition.
    c) Generating new files per connector based on defined templates.
    d) Generating a Markdown connector specification document.
  Python standard library modules used:
  - os                     (path manipulation, file/directory operations)
  - json                   (JSON parsing)
  - shutil                 (recursive directory copy)
  - sys                    (command-line arguments, exit)
  - re                     (regex for ConnectorGenerator/SpecGenerator conditional
                            block parsing, date string detection, Service-Component
                            stripping in MANIFEST.MF, import injection in the
                            converter, TOC anchor generation, and nodemanager
                            block substitution)
  - datetime               (datetime.date.today() for today's date in spec doc)
  - xml.etree.ElementTree  (XML element building for connectors.xml)
  - xml.dom.minidom        (XML pretty-printing for connectors.xml)

4. NAMING CONVENTION: src DIRECTORY PATHS
--------------------------------------------------------------------------------

When constructing src\ directory paths, any dots (.) in <projectname> must be
replaced with path separators (\). e.g. projectname "inventory.tmf"
       → src\com\telus\connector\inventory\tmf\

This applies to ALL src\ paths including:
  - src package paths in the config project
  - src package paths in the api project
  - src package paths in the implementation project
  - the api\datatypes path in the api project

Directory/project folder names and Java package declarations retain dots as-is.
The datatypes directory in the API project follows the same dots-as-separators
rule as all other src\ paths:
  src\com\telus\connector\<projectname with dots as \>\api\datatypes\
  e.g. projectname "inventory.tmf"
       → src\com\telus\connector\inventory\tmf\api\datatypes\

9. STEP 5 — GENERATE CONFIG FILES PER CONNECTOR
--------------------------------------------------------------------------------

For each <connectorid> in the connector list:

  A) Generate OSGI-INF\com.telus.connector.<projectname>.<connectorid>.xml

     Based on template: com.telus.connector.projectname.connectorid.xml.txt

     <?xml version="1.0" encoding="UTF-8"?>
     <scr:component xmlns:scr="http://www.osgi.org/xmlns/scr/v1.2.0"
         activate="configure"
         configuration-pid="com.telus.connector.<projectname>.<connectorid>.rest"
         configuration-policy="require"
         immediate="true"
         name="com.telus.connector.<projectname>.<connectorid>">
       <property name="target"
                 value="com.telus.connector.<projectname>.SvcQualification"/>
       <implementation
                 class="com.telus.connector.<projectname>.<connectorid>ConfigurationComponent"/>
       <service>
         <provide
                 interface="com.telus.connector.<projectname>.I<connectorid>ConfigurationComponent"/>
       </service>
     </scr:component>

     Token replacements:
       <projectname>  → projectname from JSON
       <connectorid>  → connectorid from JSON
     Note: "SvcQualification" in the <property> target value is a fixed literal.

  B) Generate src\com\telus\connector\<projectname>\I<connectorid>ConfigurationComponent.java

     Generated from TEMPLATE_ICONFIG_JAVA (ITemplateConfigurationComponent.java.txt),
     located at:
       $TEMPLATECONNECTORDIR\com.telus.connector.svcqualification.config\
         src\com\telus\connector\svcqualification\ITemplateConfigurationComponent.java.txt

     Processing steps:
       1. Read the template file (UTF-8, BOM-safe).
       2. Apply token replacements:
            <projectname>  → projectname from JSON
            <connectorid>  → connectorid from JSON
       3. Write the output file (UTF-8) to:
            src\com\telus\connector\<projectname>\I<connectorid>ConfigurationComponent.java

  C) Generate src\com\telus\connector\<projectname>\<connectorid>ConfigurationComponent.java

     Generated from TEMPLATE_CONFIG_JAVA (TemplateConfigurationComponent.java.txt),
     located at:
       $TEMPLATECONNECTORDIR\com.telus.connector.svcqualification.config\
         src\com\telus\connector\svcqualification\TemplateConfigurationComponent.java.txt

     Processing steps:
       1. Read the template file (UTF-8, BOM-safe).
       2. Apply token replacements:
            <projectname>  → projectname from JSON
            <connectorid>  → connectorid from JSON
       3. Write the output file (UTF-8) to:
            src\com\telus\connector\<projectname>\<connectorid>ConfigurationComponent.java

  D) Delete template .txt files from the copied config project src directory.
     After generating B) and C), delete the following files from:
       $CONNECTORDIR\com.telus.connector.<projectname>.config\
         src\com\telus\connector\svcqualification\

       - ITemplateConfigurationComponent.java.txt
       - TemplateConfigurationComponent.java.txt

     After deletion, remove the now-empty svcqualification\ directory using
     os.rmdir(). If either file is not found, print [WARN] and continue.

  E) Update META-INF\MANIFEST.MF
     Append all generated OSGI-INF filenames to the Service-Component entry,
     each prefaced with "OSGI-INF/". Format:
       Service-Component: OSGI-INF/com.telus.connector.<projectname>.<connectorid>.xml
     Multiple entries are comma-separated with a leading space continuation:
       Service-Component: OSGI-INF/com.telus.connector.<projectname>.<connectorid1>.xml,
        OSGI-INF/com.telus.connector.<projectname>.<connectorid2>.xml
     (Pre-existing template Service-Component entries were already removed in Step 2.)

10. STEP 6 — GENERATE API FILES PER CONNECTOR
--------------------------------------------------------------------------------

For each connector, generate two outputs in the API project:

  A) OSGI-INF\solvatio\connectors.xml
     Built from scratch with one <connector> block per connector definition.
     Based on template: connectors.xml.txt

     <?xml version="1.0" encoding="UTF-8"?>
     <connectors>
         <connector
                 version="1.0.0"
                 name="<connectorid>"
                 description=""
                 id="com.telus.connector.<projectname>.<connectorid>">
             <input
                     name="parameters"
                     class="com.telus.connector.<projectname>.api.datatypes.<inputClass>">
             </input>
             <output
                     class="com.telus.connector.<projectname>.api.datatypes.<dataRecordClass>">
             </output>
         </connector>
         ... (one block per connector)
     </connectors>

     Token replacements per connector:
       <connectorid>     → connectorid from JSON
       <projectname>     → projectname from JSON
       <inputClass>      → inputClass from JSON
       <dataRecordClass> → dataRecordClass from JSON

     Note: XML is built programmatically using xml.etree.ElementTree and
     pretty-printed with xml.dom.minidom. The minidom-generated XML declaration
     is replaced with: <?xml version="1.0" encoding="UTF-8"?>
     Blank lines are stripped from the output.

  B) src\com\telus\connector\<projectname with dots as \>\api\datatypes\<connectorid>Types.model

     Generated by _write_types_idl(). Structure:

       package com.telus.connector.<projectname>.api.datatypes

       import com.telus.common.api.datatypes.DataRecord
       import com.telus.common.api.datatypes.Entity

       struct <connectorid>Request {
         <IDL fields from requestExample JSON, if provided>
       }

       struct <connectorid>Entity {
         <IDL fields from responseExample JSON, if provided>
       }

       struct <connectorid>DataRecord extends DataRecord {
         <connectorid>Entity entity
       }

       ... (one set of structs per connector, plus any nested structs)

     IDL field type mapping (_json_to_idl_fields / _json_value_to_idl_type):
       bool              → bool
       int               → int
       float             → float
       str (date-like)   → string  (with // TODO: verify — looks like a date comment)
       str (other)       → string
       None              → string  (with // TODO: verify data type - all values null in sample)
       list (empty)      → string[]  (with // TODO: verify data type - empty array in sample)
       list of bool      → bool[]
       list of int       → int[]
       list of float     → float[]
       list of str       → string[]
       list of objects   → <SingularName>[]  (struct collected into top_level_structs)
       dict              → <StructName>      (struct collected into top_level_structs)

     requestExample / responseExample handling:
       - Filenames are read from the connector's "requestExample" /
         "responseExample" fields (optional — read via .get()).
       - Files are expected to be co-located with the definition JSON file.
       - If a filename is provided but the file is missing or empty, a [WARN]
         is printed and the corresponding IDL struct body is left empty.
       - If a file cannot be parsed, a [WARN] is printed and the body is
         left empty.
       - If the field is absent/null, the IDL struct body is left empty.
     definition_file path is passed into generate_api_per_connector() so that
       example files can be resolved relative to the definition directory.

11. STEP 7 — GENERATE IMPLEMENTATION FILES PER CONNECTOR
--------------------------------------------------------------------------------

For each <connectorid>, generate the following files under:
  $CONNECTORDIR\com.telus.connector.<projectname>\src\com\telus\connector\<projectname>\

  call\<connectorid>Connector.java
    Generated from TemplateConnector.java.txt (TEMPLATE_CONNECTOR_JAVA).
    Processing steps:
      1. Read the template file (UTF-8, BOM-safe).
      2. Process ConnectorGenerator conditional blocks based on httpMethod,
         keeping only the lines matching the given httpMethod and discarding others.
      3. Apply token replacements:
           <projectname>    → projectname
           <connectorid>    → connectorid
           <requestExample> → stem of requestExample filename
                              (or connectorid if requestExample is absent)
      4. Write the output file (UTF-8).
    Conditional block syntax in template:
      // ConnectorGenerator: if <httpMethod> == GET
          ... GET-specific code ...
      // ConnectorGenerator: else if <httpMethod> == POST
          ... POST-specific code ...
      // ConnectorGenerator: else if <httpMethod> == PATCH
          ... PATCH-specific code ...
      // ConnectorGenerator: end if
    Rules:
      - Only the branch whose method matches httpMethod (case-insensitive) is emitted.
      - Once a branch is matched, subsequent else-if branches are suppressed.
      - Directive lines themselves are never emitted.
      - Lines outside any conditional block are always emitted.
      - <requestExample> token appears in POST-specific blocks (e.g. import
        and instantiation of the <requestExample>Pojo class). It is replaced
        with the requestExample filename stem (or connectorid as fallback)
        after conditional block processing is complete.

  model\<requestStem>Pojo.java
    Generated by _write_pojo_java() if requestExample is provided.
    <requestStem> = filename stem of requestExample (e.g. "myRequest" from "myRequest.json").

  model\<responseStem>Pojo.java
    Generated by _write_pojo_java() if responseExample is provided.
    <responseStem> = filename stem of responseExample.

  POJO generation rules (_write_pojo_java / _json_to_pojo_fields):
      - Reads the JSON example file (UTF-8, BOM-safe).
      - If the root JSON value is a list, the first element (if a dict) is used.
      - For each top-level key/value pair, generates a private field + getter + setter.
      - Recursively generates separate <ClassName>Pojo.java files for:
          dict values     → class name = key.capitalize() + "Pojo"
                            field type = key.capitalize() + "Pojo"
                            (e.g. MetaPojo — field and class both use full Pojo suffix)
          list of objects → class name = _singularize(key).capitalize() + "Pojo"
                            field type = List<_singularize(key).capitalize() + "Pojo">
                            (e.g. List<OutagePojo>)
                            All list elements are merged to get the full field set
                            (best non-null value per key across all elements).
      - Nested POJO files are written to the same model\ directory.
      - Import statements are auto-generated based on field types used:
          Date fields       → import java.util.Date;
          List fields       → import java.util.List;
          Nested POJO types → import com.telus.connector.<projectname>.model.<NestedClass>Pojo;
      - If the file is missing, empty, or unparseable, a stub class is written
        with a // TODO: add fields comment and a [WARN] is printed.

    Java type mapping (_json_to_pojo_fields):
      bool              → boolean
      int               → long
      float             → double
      str (date-like)   → Date
      str (other)       → String
      None              → String  (with // TODO: verify data type comment)
      list of objects   → List<SingularClassNamePojo>  (generates SingularClassNamePojo.java)
      list (empty)      → List<String>  (with // TODO: verify data type comment)
      list of bool      → List<Boolean>
      list of int       → List<Long>
      list of float     → List<Double>
      list of str (date)→ List<Date>
      list of str       → List<String>
      dict              → ClassNamePojo  (generates ClassNamePojo.java)

  converter\<connectorid>Converter.java
    Generated from TemplateConverter.java.txt (TEMPLATE_CONVERTER_JAVA)
    if responseExample is provided. Otherwise a generic stub is written.
    Processing steps:
      1. Read the template file (UTF-8, BOM-safe).
      2. Process '// ConnectorGenerator: if <requestExample> != null' block:
           - If requestExample is present → keep the block body, strip directive lines.
           - If requestExample is absent  → strip the entire block including body.
           This controls inclusion of the to<connectorid>Pojo() method.
      3. Apply token replacements:
           <projectname>     → projectname from JSON
           <connectorid>     → connectorid from JSON
           <requestExample>  → stem of requestExample filename
                               (or connectorid if requestExample is absent)
           <responseExample> → stem of responseExample filename
      4. Replace 1st occurrence of "// TODO: implement the conversion logic here"
           → inside to<connectorid>Entity(): body lines only (rv.setXxx(...))
             generated from responseExample JSON.
             Maps <responseExample>Pojo → <connectorid>Entity (IDL struct).
             The template already provides 'return rv;' and the closing '}'.
      5. Replace 2nd occurrence of "// TODO: implement the conversion logic here"
           → inside to<connectorid>Pojo(): body lines only (rv.setXxx(...))
             generated from requestExample JSON.
             Maps <connectorid>Request (IDL) → <requestExample>Pojo.
             The template already provides 'return rv;' and the closing '}'.
      6. Inject private helper methods (convertToXxx) before the class closing '}'.
         Helper methods are generated for all nested objects and lists of objects
         found in the JSON examples.
      7. Inject import statements for nested API datatype structs after the last
         existing import line:
           import com.telus.connector.<projectname>.api.datatypes.<StructName>;
         One import per nested struct type discovered during conversion logic
         generation (e.g. Signal, Smartphone).
      8. Write the output file (UTF-8).

    Conversion logic generation (_json_to_conversion_logic):
      - Reads the JSON example file (UTF-8, BOM-safe).
      - Unwraps list root to first element if applicable.
      - Returns a tuple: (top_level_body, helpers_str, nested_api_types)
          top_level_body   : rv.set<Key>(...) lines for each top-level field
          helpers_str      : private convertToXxx() helper method bodies
          nested_api_types : list of nested struct type names needing imports
      - If the JSON file is missing, empty, or unparseable, returns ("", "", [])
        and the TODO comment is left unchanged.

    TemplateConverter.java.txt conditional block syntax:
      // ConnectorGenerator: if <requestExample> != null
          ... to<connectorid>Pojo() method body ...
      // ConnectorGenerator: end if
    Rules:
      - If requestExample is present: keep body, strip directive lines only.
      - If requestExample is absent:  strip entire block including body.
      - Directive lines themselves are never emitted.

  factories\<connectorid>Factory.java
    Generated from TemplateFactory.java.txt (TEMPLATE_FACTORY_JAVA).
    Processing steps:
      1. Read the template file (UTF-8, BOM-safe).
      2. Apply token replacements:
           <projectname>  → projectname from JSON
           <connectorid>  → connectorid from JSON
           <apiPath>      → apiPath from JSON
      3. Write the output file (UTF-8).

  exception\<connectorid>ConversionException.java

12. STEP 8 — GENERATE SPEC DOCUMENT
--------------------------------------------------------------------------------

Function: generate_spec_doc(projectname, connectors, definition, definition_file)
Output:   $BASEDIR\docs\<projectname>-connector-spec.md

  If TEMPLATE_SPEC_MD does not exist: print [WARN] and return (skip silently).

  Template file: $TEMPLATEDIR\ConnectorSpecTemplate.md.txt
  Read with UTF-8, BOM-safe encoding.

  Processing steps (in order):

  Step 1 — Today's date
    Replace both occurrences of:
      "//SpecGenerator: insert today's date in yyyy-mm-dd format"
    with today's date formatted as YYYY-MM-DD (datetime.date.today().strftime("%Y-%m-%d")).
    Applies to both the Document History table row and the Additional Information footer.

  Step 2 — Project description
    Replace:
      "// SpecGenerator: Insert <projectdescription>"
    with the value of "projectdescription" from the definition JSON.
    If absent or empty: replace with "_No description provided._"

  Step 3 — Connector Endpoints table
    Replace the placeholder table row containing:
      "SpecGenerator: Insert <hosts.env>"
    with one Markdown table row per host entry:
      | <env> | <hostname> | <authentication> |
    If hosts list is empty: replace with "| | | |"

  Step 4 — Nodemanager Definitions block
    Replace the entire block from:
      "// SpecGenerator: define nodemanager definition..."
    up to (but not including) the next:
      "// SpecGenerator: Insert pagebreak"
    with generated Markdown sections, one per host per connector:

      ### <env>

      #### <connectorid>
      ```xml
      <service serviceId="com.telus.connector.<projectname>.<connectorid>.rest">
          ...
      </service>
      ```

    Authentication type determines the XML block:
      - "basic" → includes endpoint, password, authenticationType=basic,
                   timeout, username=APP_SOLVATIO
      - "kong"  → includes endpoint, authenticationType=kong, timeout
      - default → kong

    endpoint value = <hostname>/<apiPath> (apiPath leading slash stripped)

  Step 5 — Connector Definitions for-each loop
    Marker: "// SpecGenerator: for each <connectorid>" ... "// SpecGenerator: end for"
    (Note: "end for" must NOT match "end for loop")
    Expands the body template once per connector, substituting:
      \<connectorid\>  → connectorid
      \<projectname\>  → projectname
      "// SpecGenerator: Insert <connectordescription>"
                       → connectordescription value, or "_No description provided._"
      "// SpecGenerator: Insert \<requestExample\>Request object definition from IDL"
                       → fenced IDL code block for <connectorid>Request struct
                         (parsed from requestExample JSON via _json_to_idl_fields)
      "// SpecGenerator: Insert \<responseExample\>Entity object definition from IDL"
                       → fenced IDL code block for <connectorid>Entity struct
                         (parsed from responseExample JSON via _json_to_idl_fields)
      "// SpecGenerator: Insert pagebreak" (inside loop)
                       → \n---\n\n

    IDL block format (_idl_block_for_spec):
      - If file is absent/empty: returns "_No example file provided._"
      - If file cannot be parsed: returns "_Could not parse example file._"
      - Otherwise: returns a fenced code block (``` ... ```) containing the
        parent struct and all nested structs (blank line between structs).
      - Appends **WARNINGS:** section for any fields with
        "// TODO: verify data type - empty array in sample" comments,
        formatted as: Unverified data type for <StructName>.<field> - empty array in sample<br>

  Step 6 — Appendix A for-each loop
    Marker: "// SpecGenerator: for each <connectorid>" ... "// SpecGenerator: end for loop"
    Expands the body template once per connector, substituting:
      "// SpecGenerator: Insert <requestExample>"
                       → raw JSON content of requestExample file in a fenced code block,
                         or "_No request example provided._" if absent/empty
      "// SpecGenerator: Insert <responseExample>"
                       → raw JSON content of responseExample file in a fenced code block,
                         or "_No response example provided._" if absent/empty
      "// SpecGenerator: Insert pagebreak" (inside loop)
                       → \n---\n\n

  Step 7 — Table of Contents
    Replace:
      "// SpecGenerator: Insert links to document sections"
    with a Markdown TOC generated by scanning all headings (# through ######)
    in the now-fully-processed template.
    Format per heading:
      <indent>- [<heading text>](#<anchor>)
    where indent = "  " * (heading level - 1)
    and anchor = heading text lowercased, non-word/non-space/non-hyphen chars
    stripped, spaces replaced with hyphens.
    If no headings found: "_No sections found._"

  Step 8 — Remaining pagebreaks
    Replace all remaining:
      "// SpecGenerator: Insert pagebreak"
    with \n---\n\n

  Step 9 — Write output
    Write final Markdown to: $BASEDIR\docs\<projectname>-connector-spec.md (UTF-8)
    Create the docs\ directory if it does not exist.
